# i18n (English / Amharic)

Tolo's three apps (`frontend`, `merchant-dashboard`, `admin-dashboard`) share
one i18n framework, built directly into `@tolo/ui` (`packages/ui/src/i18n/`).
No external i18n library — the framework is small enough that a plain React
context + two locale files covers everything needed, without adding a
dependency across all three apps.

## How it works

- **Locale files**: `packages/ui/src/i18n/locales/en.ts` (the authored
  source) and `am.ts` (Amharic). Both are flat `Record<string, ...>` keyed by
  dot-path strings like `"checkout.placeOrder"` — not nested objects. `en.ts`
  values are plain strings. `am.ts` values are `{ text, status }`, where
  `status` is `"machine_translated"` or `"reviewed"` (see "Reviewing a
  translation" below).
- **`I18nProvider`** (`packages/ui/src/i18n/I18nProvider.tsx`) wraps each
  app's root once, in `main.tsx`, outside `<BrowserRouter>`. It holds the
  active `Locale` (`"en" | "am"`) in React state, and on every change:
  writes it to `localStorage` (`tolo_locale`), sets
  `document.documentElement.lang`, and mirrors it into a plain module-level
  singleton (`i18n/locale.ts`) that non-component code (`lib/format.ts`)
  reads without needing a `locale` prop threaded through every call site.
- **`useTranslation()`** returns `{ locale, setLocale, t }`. `t(key, vars?)`
  looks up `key` in the active locale, interpolating `{{name}}` placeholders
  from `vars`. If the key is missing from Amharic, it falls back to English
  (never a blank string, never the raw key, except as an absolute last
  resort if the key doesn't exist in *either* file).
- **`<LanguageSwitcher />`** (`packages/ui/src/components/LanguageSwitcher.tsx`)
  is the one shared switcher component. `variant="compact"` (default) is a
  single-tap toggle for a tight header bar; `variant="full"` spells out both
  languages as separate buttons, for a mobile menu panel.
- **Default locale**: a stored `localStorage` preference always wins. With
  nothing stored, the browser's language decides — Amharic (`am*`) if the
  browser reports it, English otherwise. See `i18n/detectLocale.ts`.
- **Font**: Noto Sans Ethiopic, loaded via `<link>` in each app's
  `index.html` (Google Fonts, `rel="preconnect"` for latency), with a
  `system-ui` fallback stack. Applied automatically via a `:lang(am)` CSS
  rule in `packages/ui/src/theme.css` — no class toggling needed, since
  `I18nProvider` already sets `<html lang="am">`.
- **Formatting** (`packages/ui/src/lib/format.ts`): `formatDate`,
  `formatDateTime`, and `formatRelativeTime` read the active locale
  automatically (via the singleton) and translate their own words ("just
  now", "min ago", etc.) and month names. `formatCurrency`'s numeral
  grouping is deliberately locale-invariant — ETB amounts use the same
  Western Arabic numerals and comma grouping in both languages, so there's
  nothing to switch. `formatDateEthiopian(value, locale?)` is a separate,
  **opt-in** function for the Ethiopian calendar (`Intl.DateTimeFormat`
  with the `ethiopic` calendar extension) — Gregorian stays the default
  everywhere; nothing calls this automatically.

## Adding or changing a string

1. Add the key to `packages/ui/src/i18n/locales/en.ts` (plain string).
2. Add the **same key** to `am.ts`, wrapped in the file's `mt(...)` helper
   (sets `status: "machine_translated"`).
3. Use it in a component via `const { t } = useTranslation(); t("your.key")`.
   For interpolation: `t("orders.orderLabel", { orderNumber: "TL-1234" })`
   with `"{{orderNumber}}"` in the string.
4. Run `npm test --workspace=packages/ui` — `i18n-key-parity.test.ts` fails
   the build if `en.ts` and `am.ts` don't have exactly the same key set.

Never hardcode a user-facing string directly in a component. The one
deliberate exception: **user-generated content** — product names,
descriptions, shop names, review text — is never translated and is never
routed through `t()`; it's rendered exactly as the customer/merchant/admin
entered it.

## Reviewing a translation

Every string in `am.ts` currently carries `status: "machine_translated"` —
none of it has been checked by a native or professional Amharic speaker, and
the legal-document strings (`legal.terms.*`, `legal.privacy.*`,
`legal.refund.*`) are additionally still pending the same legal review the
English placeholder text itself needs (see `LegalPage.tsx`'s own banner).
To mark a string reviewed, change its `status` to `"reviewed"` in `am.ts` —
no other code changes needed.

## What's translated in this pass

Framework, language switcher (every app's header + mobile menu), and a
substantial set of real screens: the customer app's navigation, cart,
checkout (including rider tips and the out-of-stock substitution choice),
orders list/detail, order confirmation, login/signup/password-reset, and
the Terms/Privacy/Refund pages; the merchant app's navigation, order detail
(including the substitution-resolution flow), and the reported-issues page;
the admin app's navigation chrome (language switcher, sign out, change
password).

**Known gaps**, left for a follow-up pass rather than left silently
untranslated:
- The admin dashboard's page navigation labels and the Users & Roles
  permissions checklist are still English-only — Tolo staff are the
  audience there, not customers, and it was lower priority than the
  customer/merchant surfaces above within this pass's scope.
- Several secondary customer pages (Favorites, Notifications, Saved
  Locations, Support ticket form, product/shop browsing detail pages) and
  most of merchant-dashboard's and admin-dashboard's remaining pages
  (Products, Promotions, Wallet, Store Settings, Merchants, Payments,
  Refunds, Settlements, etc.) are not yet wired to `t()`.
- **Backend error mapping**: edge functions (`supabase/functions/*`) return
  plain English error strings today (e.g. `checkout/index.ts`'s
  `sanitizeOrderError`). The `errors.*` keys in `en.ts`/`am.ts` already hold
  translated equivalents for the known, enumerable set of these messages,
  but no client-side call site yet routes a caught server error through a
  lookup against them — every `toast.error(...)` in edge-function error
  handlers today still shows the raw English string regardless of locale.
  Wiring this up means adding a small `translateServerError(message,
  locale)` helper (matching the known English strings to their `errors.*`
  key) and applying it at each `toast.error()` call site that surfaces a
  caught Edge Function error — mechanical, but touches many files, and
  wasn't completed in this pass.

## Tests

- `packages/ui/src/i18n/i18n-key-parity.test.ts` — fails if any key exists
  in `en.ts` but not `am.ts` (or the reverse), if any English string is
  empty, if an Amharic entry is malformed, or if a `{{placeholder}}` in an
  English string doesn't have a matching one in its Amharic counterpart.
- `packages/ui/src/i18n/I18nProvider.test.tsx` — browser-language default
  detection (Amharic vs. English), a stored preference overriding the
  browser default, switching the language persists it to `localStorage`
  and sets `<html lang>`, and the English fallback for a key missing from
  Amharic.
- `packages/ui/src/i18n/no-hardcoded-strings.test.ts` — for each page this
  Group 5 pass touched, asserts it imports `useTranslation` and no longer
  contains the specific English literals it used to render directly.

Run them with `npm test --workspace=packages/ui` — this suite is pure UI
(jsdom, no database), so it runs and is verified locally, unlike this
repo's backend smoke-test suite (`tests/smoke/*`, see `tests/README.md`).
